# 测试与排错

## 优先测试顺序

1. 构建真实改包，确认 runtime + companion Java 没有编译错误。
2. 在 Emulator 安装测试壳，确认悬浮窗 UI、拖动、长按设置、广播回放可用。
3. 构造真实改包 APK，确认签名验证通过。
4. 在 ARM/ARMv7 兼容车机或环境安装真实改包，验证高德启动和悬浮窗替换。

## 测试壳

```powershell
.\build-test-apk.ps1
adb -s emulator-5554 install -r -t .\dist\amap_auto_patch_vm_test.apk
adb -s emulator-5554 shell appops set amap.auto.patch.test SYSTEM_ALERT_WINDOW allow
adb -s emulator-5554 shell monkey -p amap.auto.patch.test -c android.intent.category.LAUNCHER 1
```

查看日志：

```powershell
adb -s emulator-5554 logcat -s AmapAutoPatch
```

整合版 companion 运行日志也可看：

```powershell
adb -s emulator-5554 logcat -s AmapCompanion
```

## 广播回放

导航：

```powershell
adb -s emulator-5554 shell am broadcast -a AUTONAVI_STANDARD_BROADCAST_SEND --ei KEY_TYPE 10001 --es NEXT_ROAD_NAME "人民路" --ei SEG_REMAIN_DIS 320
```

红绿灯：

```powershell
adb -s emulator-5554 shell am broadcast -a AUTONAVI_STANDARD_BROADCAST_SEND --ei KEY_TYPE 60073 --ei trafficLightStatus 2 --ei redLightCountDownSeconds 12 --ei dir 4 --ei lightsCount 3
```

巡航：

```powershell
adb -s emulator-5554 shell am broadcast -a AUTONAVI_STANDARD_BROADCAST_SEND --ei KEY_TYPE 60021 --es ROAD_NAME "中山路" --ei CUR_SPEED 42 --ei LIMITED_SPEED 60
```

前后台状态：


## 确认悬浮窗窗口存在

```powershell
adb -s emulator-5554 shell dumpsys window windows | findstr /i "amap.auto.patch"
```

测试壳应能看到 `amap.auto.patch.test` 的 overlay 窗口。真实高德内应看到目标包名相关窗口。

## 常见问题

### SHA-256 mismatch

输入 APK 和 profile 不一致。不要跳过这个检查。为新 APK 新建 profile，并重新找 smali marker。

### apktool.jar not found

把 apktool 放到：

```text
tools/apktool.jar
```

或传入：

```powershell
.\patch.ps1 -ApktoolJar C:\tools\apktool.jar -InputApk D:\path\to\amap.apk
```

### patch marker not found

目标高德版本的 smali 变了。按 [[如何适配新版本]] 重新查找 `Application.onCreate`、原悬浮窗 `addView`、红绿灯 wrapper 和清理方法。

### 改包比原包大很多

检查 `apktool.yml` 里的 `doNotCompress` 是否仍包含 `so`。真实构建会自动移除 `so`，让 native 库继续压缩。如果误关了这一步，APK 可能明显变大。

### Emulator 安装真实改包失败

当前真实 APK 包含 `armeabi-v7a` native 库，普通 x86/x86_64 Emulator 不适合作为真实运行环境。用测试壳验证 UI，用 ARM/ARMv7 兼容环境验证真实改包。

### 悬浮窗不刷新

检查：

- `logcat -s AmapAutoPatch` 是否有 `runtime initialized`。
- `logcat -s AmapCompanion` 是否有 companion 服务启动和广播处理日志。
- 发送的广播 action 是否是 `AUTONAVI_STANDARD_BROADCAST_SEND`。
- 导航广播是否带 `KEY_TYPE=10001`。
- 红绿灯 wrapper 注入点是否执行。
- 红绿灯数据是否被 `hasValidTrafficLight()` 判定为无效。

### 红绿灯不显示

优先看 wrapper：

- `trafficLightPatch` 是否插入成功。
- `PatchBridge.wrapperToExtras(...)` 中字段 `a/d/e/c` 是否仍匹配当前版本。
- 倒计时或状态是否大于 0。

广播红绿灯字段只是兼容路径，实车上不一定稳定发送。

### 两个高德车机版同时安装

Android 广播按 action 分发，动态注册的接收者都可能收到同一条标准广播。这个改包运行在被修改的高德进程里，是否会收到另一份高德发出的广播，取决于系统广播分发和 action 是否相同。红绿灯 wrapper 是进程内部注入，只会来自当前改包进程；标准广播则可能被同 action 的多个应用接收。

如果需要隔离多高德场景，建议在 `OverlayService` 的广播处理逻辑中增加额外判断，例如校验包名、进程状态、或只信任内部 wrapper 的红绿灯数据。
