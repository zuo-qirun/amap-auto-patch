# 方法介绍

## 总体思路

本项目不是重新开发一个外部悬浮窗应用，而是把一个很小的运行时注入到高德车机版 APK 内。高德创建原悬浮窗时，补丁把原来的 `WindowManager.addView(...)` 调用替换为 `PatchRuntime.replaceHostFloatWindow(...)`。运行时接管窗口创建，显示自己的 `OverlayController` 面板。

## 代码分层

- `patch.ps1`：完整 APK 构造流水线，负责校验输入 APK、编译 runtime、反编译 APK、应用 smali 补丁、回编、zipalign、签名和验证。
- `profiles/9.1.0.600087.json`：版本适配 profile，记录目标 APK SHA-256、包名、输出名、smali 文件和插入标记。
- `runtime/src/main/java/amap/auto/patch/PatchRuntime.java`：注入后的运行时入口，注册广播、替换原悬浮窗、接收红绿灯 wrapper。
- `runtime/src/main/java/amap/auto/patch/OverlayController.java`：悬浮窗 UI、样式、轮播、设置面板、拖动保存位置。
- `runtime/src/main/java/amap/auto/patch/DataModel.java`：把广播 extra 或高德内部 wrapper 转成统一显示模型。
- `build-test-apk.ps1` 和 `test_app/`：虚拟机测试壳，用来不依赖高德主程序验证 runtime UI。

## 注入点

当前 profile 使用四个 patch：

- `applicationPatch`：在 `MapApplicationProxy.onCreate()` 后插入 `PatchRuntime.init(context)`，保证高德启动时运行时初始化。
- `hostFloatWindowPatch`：把原悬浮窗的 `WindowManager.addView(view, params)` 替换成 `PatchRuntime.replaceHostFloatWindow(wm, view, params)`。
- `trafficLightPatch`：在高德内部红绿灯 wrapper 更新后插入 `PatchRuntime.onTrafficLightWrapper(wrapper)`。
- `hostFloatWindowCleanupPatch`：原悬浮窗关闭时同步调用 `PatchRuntime.removePatchOverlay()`。

## 数据来源

运行时使用两类数据：

- 标准动态广播：监听 `AUTONAVI_STANDARD_BROADCAST_SEND`，由 `DataModel.fromBroadcast(...)` 解析导航、巡航、车道和前后台状态。
- 高德内部对象：在红绿灯 wrapper 更新位置直接注入调用，由 `DataModel.fromTrafficLightWrapper(...)` 通过反射读取字段。

红绿灯优先使用内部 wrapper，因为实际测试中标准广播未必稳定透出红绿灯倒计时。导航仍按标准广播读取。

## APK 构造方式

runtime 先由 `javac` 编译为 class，再由 `d8` 转成 `runtime.dex`。脚本用 apktool 把 `runtime.dex` 转成 smali，复制到原 APK 解包目录的 `smali/amap/...` 下，最终和原 `classes.dex` 一起由 apktool 回编。

这样做的原因是只改一个 dex 的 smali 结构，避免直接往 APK 里追加新的 `classes2.dex` 后触发安装解析或签名校验兼容问题。
